How to submit

The binding format sentences, the build routes, the 13-gate checklist, and the fix for the [0, 1] rejection. Nothing here is from memory — every rule sentence links to its official page.

1. The format the platform requires

Per the official submission format and rules §3.2–§3.3:

RequirementValueEnforced by
Filesingle-band GeoTIFF (.tif), or .zip containing onegate 1–2
CRSEPSG:32611 (UTM 11N), same as training datagate 4
Resolution100 m, same bounds as training datagates 5–7
Outside boundsnull / NaNgates 8, 13
Dtype + rangefloat32, values in [0, 1], higher = more likely faultgates 3, 9–10
Templatea sample submission (total fault absence) is provided as the templategate 11

Grid shape/transform/footprint-size numbers are read from the template file at validation time — this repo never hard-codes them as truth (sibling-quoted values 3730×3292 etc. are labelled UNVERIFIED until our own template lands; see flagged items).

2. Build routes (pick one)

Route A — score field → submission (normal)

# 1. produce scores.npy (same HxW as the template) with your model, then:
python scripts/build_submission.py --strategy topk_hard@0.03 --scores scores.npy --out submissions/ \
  --note-extra "H1 gravity edges, holdout-best"
# 2. re-verify independently of the builder:
python scripts/validate_submission.py submissions/*.tif --template data/sample_submission.tif

Route B — ZIP it (the dialog accepts a single-member ZIP)

cd submissions && zip gems8-topk_hard-....zip gems8-topk_hard-....tif && cd ..

Route C — smoke test the pipeline without data

python scripts/build_submission.py --strategy topk_hard@0.03 --demo --out submissions/
python scripts/validate_submission.py --self-test   # GOOD passes 13/13; 3 BAD fixtures rejected
python -m pytest tests/ -q                          # 17 tests incl. official worked example

Every build gets a unique name (gems8-<strategy>-<UTC instant>-<payload sha8>.tif) and a paste-ready Note (8GEMSDOE <strategy> | <sha8> | …), recorded with both hashes in reports/submissions_log.json.

#GateWhat it checks

5resolution-100m|pixel| = 100 m in x and y
6shapeHxW identical to template

Implementation: src/gems/submission.py (tifffile-based, no GDAL needed), CLI: scripts/validate_submission.py.

4. The [0, 1] rejection — cause and fix

Symptom. The submission form answers Predicted values must be in range [0, 1].

Cause. A pixel inside the scored footprint is NaN (or <0, or >1). NaN is legal only outside the footprint. This is gate 12 above.

Fix (structural, in the builder). conform_to_template() runs on every build, before validation:

  1. clip finite values into [0, 1] (counts reported),
  2. fill NaN-inside with 0.0 (count reported as a warning — a correct model should never produce it),
  3. force NaN-outside and GDAL_NODATA=nan,
  4. run all 13 gates; the file is deleted, not published, if any gate fails.

Manual recovery for a file built elsewhere: re-run it through conform_to_template (or rebuild with --scores) and re-validate. Do not hand-edit bytes.

5. Upload click path + weekly discipline

  1. Open DrivenData → GEMS → Submissions while signed in.
  2. Click New submission / File to submit, choose the .tif (or single-member .zip).
  3. Paste the builder's Note into the comment box. Submit.
  4. Record the returned score in reports/submissions_log.json against the payload hash.

Limits that bind us: 3 submissions/week; one final submission per entity across both rounds, chosen without knowing private scores (rules §3.4, §3.5, §3.6.2). One entity = one final submission — individuals on a team may not submit a separate final (§3.4). This repo's policy: at most one slot/week, holdout winner only, every payload hash unique (the builder refuses byte-duplicates after the GEMSDOE/5GEMSDOE 0.1563 lesson — see Leaderboard).
