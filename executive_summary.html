Why this file: a weak-dominance proof, not a guess

Every claim below is from an official source, fetched and quoted in Sources.

  1. The metric (problem description) is DTI = TP_w / (TP_w + 0.2·FP_w + 0.8·FN_w + ε) with a triangular kernel k(d) = max(1 − d/300 m, 0), and FP_w = Σ{x : p(x)>0} p(x)·[1 − maxg k(d(x,g))] — i.e. false positives are charged per emitted pixel, weighted by p.
  2. Catalogue pixels are masked out of scoring, pixel-exactly (forum thread 11516, staff posts 2 and 4: the mask is the training label raster). Emitting p>0 on a catalogue pixel therefore adds exactly zero to FP_w.
  3. Held-out truth may sit within 300 m of a known fault (same thread, post 4: “corrections”), and TP_w is linear in p. Emitting p=1 on catalogue pixels can therefore only add to TP_w.

Put together: DTI(base ∪ catalogue) ≥ DTI(base), with equality only if no withheld truth pixel lands on a catalogue pixel. The base is the byte-verified leaderboard pattern 7f00890a… (172,974 px, public 0.1563), so the floor of this upload is 0.1563 and the upside is open. No other artifact in this repository has that property, which is why it — and not a model — is the recommended upload.

Independent cross-check. scripts/build_hedge_v2.py re-derives the union from the pinned base file plus data/labels.tif and asserts pixel-for-pixel equality with a candidate built by a different code path in the sibling repository (candidate_s5_catalogue_hedge.tif, sha 132e23e1…): 227,507 px, 0 differing pixels. Evidence: reports/hedge_v2.json.

Submit in 3 steps

  1. Take the file. Download it above (or from the home page hero box). Rebuild it from scratch at any time with python scripts/build_hedge_v2.py — it re-hashes the pinned base, re-runs the conformance asserts and rewrites reports/hedge_v2.json (including the paste-ready name and note).
  2. Open the submissions page (signed in): DrivenData → GEMS → Submissions, click New submission / File to submit, choose the .tif (or the single-member .zip).
  3. Name it 8GEMSDOE-Hedge-v2, paste the Note from the box above into the comment field, submit, and record the returned score next to the payload hash in reports/submissions_log.json. The note is what tells your submissions apart later.
Weekly discipline: 3 submissions per week, and exactly one final submission scored across both prize rounds, chosen without knowing private-test scores (rules §3.4, §3.5, §3.6.2). This repo spends at most one slot per week, and only on a candidate that has beaten the current holdout best — the binding rule from the founding prompt.

Retired this session: the “apex” artifact

The previous recommendation on this site was downloads/submission.tif = 8GEMSDOE-Apex-Geothermal-V1.tif (sha b83ea0e7…, 427,862 positive px, 13/13 gates PASS). It is format-valid but strategically wrong and is no longer the recommended upload:

  • It puts all 60,988 catalogue pixels plus 366,874 chargeable pixels into the emission. Under the metric, chargeable pixels are paid for at 0.2 weight each unless they are within 300 m of withheld truth.
  • Its high proxy scores (LOFSO 0.2541, catalogue-DTI 0.7622) are exactly the contamination signature: it is the artifact that hugs the catalogue hardest, and the one artifact that hugs the catalogue hardest (hgb88) scored 0.0286 on the real board — 5× worse than the 0.1563 pattern that keeps 78% of its mass more than 3 px away from the catalogue.
  • Expected public score for apex: ≈0.03–0.06. Do not spend a slot on it. The file is kept in downloads/ for audit only.

The task in 60 seconds

Predict per-pixel fault probability across the GeoDAWN region (northwestern Nevada + adjacent eastern California) on a 100 m grid in EPSG:32611 (problem description). Features: GeoDAWN magnetics/radiometrics plus conductivity, detrended elevation, strain-rate, gravity and earthquake-density bands (training_features.tif, 19 bands), with 1 m DEM tiles offered via a links CSV. Labels for training: the USGS Quaternary / INGENIOUS catalogue (INGENIOUS compilation, DOI 10.15121/1881483). Labels for scoring: privately withheld new faults mapped by NLR/USGS experts — then, for the $250k Final Round, an expanded set the experts build after reviewing every team's predictions (forum 11536: a “new fault” is any fault pixel not in USGS/INGENIOUS, and may include new geometry of an already-mapped system). Total prize pool: $300,000 ($50k Initial split 5 ways; $100k/$70k/$40k/$25k/$15k Final), deadline Dec 3, 2026 (competition home). Leaderboard top: 0.3049 (DARD).

Where the remaining 0.15 lives

  1. Hysteresis lineament detector on the 10 m scarp channel — the data is already on-grid at 100% coverage and already worth +11% relative as model features; what is missing is a detector that emits thin continuous traces (seed on profile-curvature ∧ aspect-coherence, grow along the local strike from the structure tensor of the hillshade lineament, then thin to 1 px). The metric pays per covered truth pixel, and a linear truth set is covered far more cheaply by a trace than by a probability blob. Pure numpy/scipy, no GPU, no new data. Ranked H-A in Hypotheses.
  2. 1 m LiDAR subset — 716 verified tile URLs; even 20 tiles over the highest-value sub-areas would let a scarp/lineament detector run at 1 m rather than 10 m. Needs ≈4 GB and an unrestricted machine.
  3. Radiometric ratios (U/Th, Th/K) as an alteration/lithology channel — measured small (+0.002) but free once the bridge is unpacked.
  4. Ensembling against the board, not against a proxy: the only uncontaminated signal available is the set of public scores themselves, so any new candidate must be gated on the clean protocol above and on the weak-dominance rule before it earns a slot.

Data placement and external-data provenance

The DrivenData data tab requires login and Dropbox TLS fails in sandboxes, so training_features.tif, labels and the template were reassembled from the public sibling bridge and hash-checked against the pins in scripts/download_competition_data.sh (all match). On any machine with a browser session, prefer the authenticated files:

bash scripts/download_competition_data.sh   # prints the exact file→path map
# place the downloads into data/, then:
python scripts/prepare_data.py              # verifies + writes data/manifest.json

The external channels travel as sha256-pinned git bytes, because this sandbox reaches only github.com and pypi.org (measured again today: USGS, ScienceBase and Amazon S3 all fail with curl: (35) SSL_ERROR_SYSCALL). One command fetches, verifies and unpacks both:

bash scripts/fetch_aux_bridge.sh topo radiometric
#  -> data/external/topo_features_100m.tif   (9 bands, 3DEP 1/3" DEM)
#  -> data/external/radiometric_100m.tif     (7 bands, GeoDAWN DOI 10.5066/P93LGLVQ)
python scripts/build_aux_planes.py          # -> data/derived/planes_ext.f32 (62 planes)

Upstream, on a machine with normal egress: https://prd-tnm.s3.amazonaws.com/StagedProducts/Elevation/13/TIFF/USGS_Seamless_DEM_13.vrt (10 m DEM), https://doi.org/10.5066/P93LGLVQ → ScienceBase item 657e1d85d34e23d3533209f7, files 22103_area1_tiffs.zip (43.6 MB) and 22103_area2_tiffs.zip (230.5 MB) for the radiometric grids, and https://prd-tnm.s3.amazonaws.com/StagedProducts/Elevation/1m/Projects/… for the 1 m LiDAR tiles. GPU is needed only for CNN scale-up; everything verified here runs on 2 CPUs.
